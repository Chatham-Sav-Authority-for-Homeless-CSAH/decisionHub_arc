PWA vs. Native Mobile App

CSAH Partner App — Internal Decision Document  ·  May 2026

Context

The CSAH partner app serves ~50 users: CSAH outreach staff, SPD HOPE unit officers, CCPD behavioral health units, city/county code enforcement, and community paramedicine. These are boots-on-the-ground field workers across multiple agencies — including government agencies that may have restrictions on what software their devices can run.

Key Definitions

Native app: Software built specifically for one platform (iOS or Android) and installed through the App Store or Google Play, giving it full access to device hardware and OS features.

PWA (Progressive Web App): A website built with modern web technologies that behaves like an app — installable from the browser, works offline, and can receive push notifications — no app store needed.

Push notification: An alert sent directly to a user's device by the app — instant, free per-message, but requires the app to be installed and the OS to support it (iOS support is limited on PWAs).

SMS: A text message sent over the carrier network. Works on any phone regardless of app installation, but costs per message and replies can't be link back to the case record or maitained in app.

Messaging Strategy: SMS + Push

Outreach messaging: Regardless of which platform is chosen, outreach workers need to be able to text resource links and information directly to individuals experiencing homelessness from within the app. Since approximately 70% of the unhoused population has a smartphone, SMS is the primary bridge between the partner app and the people it serves.

Partner coordination (push): Push notifications is the desired primary communication channel between partner agencies — CSAH outreach, SPD HOPE unit, CCPD behavioral health, and others. Unlike personal texts, push notifications are tied to case records, keeping all communication in context and out of individual phones.

Push notification fallback: If an SMS provider is already in use for outreach messaging, adding SMS as a fallback for partner push notifications would require minimal additional effort — the infrastructure would already be in place. This matters for the PWA vs. native decision (see below).

At an estimated volume of ~250 messages/month, Twilio costs roughly $20–50/month. Adding push notification fallback adds negligible volume on top of that. The recommendation is to build both — push for speed and in-app experience, SMS as the safety net. This significantly reduces the risk of choosing a PWA, since the hardest knock against it (iOS push reliability) is effectively neutralized.

Factor-by-Factor Comparison

🔔 Push Notifications Critical Factor — Mitigated by SMS

PWA
Possible but friction-heavy on iOS. Users must manually add the PWA to their home screen before you can even ask for notification permission — easy to skip, hard to enforce. Subscriptions can drop if the app hasn't been opened in a while. Android via Chrome is reliable; iOS is the weak link.

However: with SMS as a fallback, a missed push still reaches the user via text. This significantly reduces the practical risk of choosing PWA.
React Native + Expo
Fully reliable on both iOS and Android via Expo Push Notifications or Firebase (FCM). Same infrastructure as full native. Subscriptions are stable. This is the primary reason to choose Expo over a PWA for this app.
Full Native (Swift + Kotlin)
Identical reliability to Expo for push notifications. No meaningful advantage over Expo here — both use FCM/APNs under the hood.
CSAH Impact Push notifications are the core coordination mechanism — SPD HOPE alerting CSAH outreach, CCPD dispatching, real-time crisis response. This is not a "nice to have" alert; it's the primary reason the app exists. PWA push reliability on iOS was the primary concern with that option — but since SMS is already planned as a separate feature (sending resources to individuals), using it as a push fallback costs almost nothing extra and neutralizes that risk. A missed push still reaches the worker via text. Open question: is receiving both a push and an SMS for every alert too invasive? Should this be a user preference?

🏛️ Government Device Restrictions Critical Factor

PWA
Runs in a browser — no app store, no MDM policy needed. Any device with Chrome or Safari can access it. Government-issued devices that block third-party app installs can still use a PWA with zero IT involvement.
React Native + Expo
Requires app store installation or MDM distribution — same challenge as full native. Officers on locked-down government devices would need their agency's IT to approve and push the app. This is a real hurdle and the biggest unknown for this option.
Full Native (Swift + Kotlin)
Same situation as Expo — requires app store or MDM. No advantage or disadvantage here relative to Expo.
CSAH Impact SPD and CCPD officers use agency-issued devices with IT-controlled policies. If those policies block non-approved app installs, a native app may never reach the people who need it most — without lengthy IT approval processes at each agency. This is still an open question and may be the single most important factor in the decision.

💰 Development Cost & Speed PWA Advantage

PWA
One codebase, all platforms. Fastest to build and deploy. No app store accounts or review process. Updates go live instantly — push a fix and users see it on next load.
React Native + Expo
One TypeScript/React codebase for iOS + Android — familiar stack, not "build twice." Expo's Over-the-Air (OTA) system pushes most updates instantly without app store review. Only native code changes (rare) require a full store submission. Requires Apple Developer account ($99/yr) and Google Play account ($25 one-time).
Full Native (Swift + Kotlin)
Two separate codebases — every feature built twice in different languages. All updates go through app store review. Highest development cost and longest timeline. Not practical for this scope.
CSAH Impact Budget is finite and the December 2026 deadline is firm. A PWA is faster and cheaper to ship initially. React Native with Expo bridges much of the gap if native is chosen — it's not "build twice."

📶 Offline Access Native Advantage

PWA
Limited offline capability via service workers. Can cache static content (e.g., resource directory), but real-time features like messaging and case updates require connectivity regardless.
React Native + Expo
Better offline-first architecture. Can queue logged actions locally and sync when connectivity is restored. Meaningful advantage for field workers in low-signal areas.
Full Native (Swift + Kotlin)
Same offline capability as Expo — can queue and sync. No practical advantage over Expo for this use case.
CSAH Impact Field workers may be in areas with spotty connectivity. The resource directory could be cached either way. Case logging and push notifications require connectivity regardless of platform — so this is a moderate factor, not a decisive one.

📍 Geolocation (One-Time Pin Drop) Tie

PWA
Browser Geolocation API is fully supported. Prompts for permission on first use. Works fine for a one-time coordinate capture.
React Native + Expo
Native geolocation with a cleaner, more familiar permission flow for users. Functionally equivalent to PWA for a one-time pin drop — no meaningful advantage in this use case.
Full Native (Swift + Kotlin)
Same as Expo. All three options handle a one-time pin drop equally well.
CSAH Impact The use case is simple: officer drops a pin when making contact with an individual. This does not require continuous background location. All three options handle it equally well.

🚀 Distribution & Updates PWA Advantage

PWA
Share a URL — anyone can access it immediately. No app store accounts, no approval process, no IT coordination. Updates deploy instantly; users always have the latest version on next load.
React Native + Expo
Requires Apple Developer ($99/yr) and Google Play ($25 one-time) accounts. Initial install goes through the app store or MDM. However, most updates ship via Expo OTA — users get them automatically without doing anything, and without waiting for store review.
Full Native (Swift + Kotlin)
Same store accounts required. Every update — including minor bug fixes — goes through app store review. Two separate release pipelines to manage. Most operationally burdensome option.
CSAH Impact Onboarding 50 users across 5 agencies is operationally easier with a URL than coordinating installs across multiple IT departments. App store accounts are a minor cost but the review and approval process adds lead time.

Summary — Three Options

PWA — Recommended default

  • No install required — works in any browser, zero IT coordination needed
  • Fastest and cheapest to build and deploy — important given budget and December deadline
  • iOS push friction is real but acceptable: SMS fallback ensures critical alerts always land
  • Avoids the government device distribution problem entirely
  • Push + SMS duplication should be a user preference — not forced on everyone by default

React Native + Expo — Upgrade path if MDM allows it

  • Cleaner push notification experience — no home screen setup friction for users
  • Better offline support — can queue case logs locally when connectivity is spotty
  • OTA updates for most changes without app store review
  • Worth pursuing only if device policy confirms officers can install third-party apps
  • Adds cost and setup complexity that isn't justified unless the PWA path is blocked

Full Native (Swift + Kotlin) — Likely Overkill

  • Maximum performance and full access to every platform API
  • Two separate codebases — iOS in Swift, Android in Kotlin — doubles development effort
  • No shared code with a potential future web or kiosk interface
  • Realistic for large teams with platform specialists; not practical for this scope or budget

Our Current Lean

With SMS fallback in the plan, the strongest argument against PWA is gone. A missed push notification still reaches the worker via text — message delivery is covered either way. That shifts the default recommendation to PWA: it's faster to build, cheaper to run, and sidesteps the government device distribution problem entirely.

Expo's remaining advantages — cleaner push UX, better offline queuing — are real but not decisive for a 50-user internal coordination tool with a hard December deadline. The offline gap matters only if field workers regularly lose connectivity long enough that they need to queue multiple case logs; worth asking, but not a safe assumption either way.

Recommendation: build PWA + SMS. If device policy confirms Expo is distributable to all agencies, revisit — but don't wait on that answer to start building.

Before Deciding

1. Confirm device policies with SPD HOPE and CCPD IT — this is a 1–2 question conversation that should happen early.

2. Decide on notification preferences: should users be able to choose push only, SMS only, or both? Receiving a push and an SMS for every alert could feel invasive without opt-in control. This may be a worthwhile feature regardless of platform choice.

Open Questions to Resolve

  1. Government device policies: Can SPD HOPE and CCPD officers install third-party apps on their issued devices, or are those devices MDM-locked? This is the single most important question — it determines whether Expo is even on the table.
  2. SMS cost at scale: Confirm Twilio pricing is not cost-prohibitive when push notification fallback volume is added on top of resource-sharing SMS volume. Estimated combined volume is still low (<500 msg/month), but worth verifying before assuming it's negligible.
  3. Notification invasiveness: Is it acceptable to send both a push notification and an SMS for every critical alert? For a high-frequency coordination tool, receiving duplicate alerts on two channels could feel intrusive. Should workers be able to set a preference (push only / SMS only / both)?
  4. User preference feature: If we build notification preferences, what are the right defaults? Push-only seems reasonable for Expo users; SMS-only as a fallback default for PWA users who haven't set up home screen notifications.
  5. Distribution ownership: If Expo is chosen, will CSAH manage app distribution centrally, or does each partner agency handle installs for their own staff?
