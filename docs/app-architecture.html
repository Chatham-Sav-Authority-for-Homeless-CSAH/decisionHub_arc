CMS vs Custom: Approach & Structure

CSAH Compass Project — Internal Decision Document  ·  June 2026

The Setup

Two distinct user surfaces, one Supabase data source. The resource directory, service availability, and weather/emergency alerts are authored once and consumed by both. Everything else — the interaction model, the feature set, and the UI — is built for two fundamentally different audiences in two fundamentally different environments.

CSAH Staff App (PWA) — CSAH outreach team (MVP)

  • CSAH outreach staff and case managers — MVP audience only
  • Case tracking, CSAH-internal messaging, push notifications, annual survey tool
  • Management dashboard, geolocation, resource directory
  • Weather alerts: exact UI treatment TBD — workers coordinate the response
  • Full PWA: installable, push-capable, offline-resilient
  • Partner agencies (HOPE, CCPD, etc.) are a future expansion phase

Kiosk App (SPA) — unhoused individuals

  • Public outdoor touchscreen stations
  • One primary function: resource directory
  • No login, no case data, no partner functionality
  • Weather alerts: prominent alert experience needed — specific format TBD
  • SPA vs. lightweight PWA: still under evaluation

Same alert data, different presentation

An inclement weather or emergency alert is created once by CSAH staff and updated in the database. Both surfaces subscribe and react immediately — but for different audiences. On the kiosk, unhoused individuals likely need a prominent, hard-to-miss alert directing them to emergency resources. In the partner app, workers need to know an alert is active so they can coordinate the response.

The architecture is settled: one alert record in Supabase, both surfaces react to it. The presentation layer is an open design question.

Part 1 Custom Web App vs. Kiosk Content Platform

The foundational question: do we build our own app that runs on the kiosk, or use a kiosk platform's built-in content tools?

Two patterns in the industry

Pattern 1 — Custom web app: You build a web application (PWA or SPA) and the kiosk hardware runs it inside a locked-down browser. The kiosk software (Scalefusion, KioWare, etc.) is purely a container — it restricts the device to your URL and handles remote management. Your app makes API calls to the database exactly the same way it would on any browser.

Pattern 2 — Kiosk content platform: A platform like Intuiface provides a visual layout builder and template system. Non-developers design screens by configuring templates, and the platform can pull data from external APIs to populate them. The platform IS the app layer — you're not writing code, you're configuring a CMS-style tool.

🎨 UI Control & Custom Experience Pattern 1 Advantage
Pattern 1 — Custom Web App
Full control over every pixel. The kiosk displays exactly what you build — large touch targets, simplified navigation designed for users who may have limited tech experience, custom visual language appropriate for the population. You are not constrained by a template system.
Pattern 2 — Kiosk Content Platform
UI is constrained by the platform's template library. You configure within their system rather than designing freely. Templates are built for general use — not specifically for unhoused individuals who may have limited reading ability, need large targets, or require a trauma-informed UX approach.
CSAH Impact The kiosk audience — people experiencing homelessness — may have limited technology experience, literacy challenges, or be in a stressed state. The UI needs to be purpose-designed for them: large text, minimal choices, clear hierarchy, culturally appropriate. A template builder doesn't give us that.

🔗 Shared Code with the Partner App Pattern 1 Advantage
Pattern 1 — Custom Web App
The resource directory is built once as a shared component — the same React components, the same Supabase data hooks, the same logic — consumed by both the partner app and the kiosk app. Updates to the resource directory automatically apply to both surfaces.
Pattern 2 — Kiosk Content Platform
The kiosk platform has its own template system. Any resource directory logic you need in the partner app has to be built separately there, in code. The two surfaces cannot share a component library — they live in entirely different technological worlds.
CSAH Impact The resource directory is the shared core of both surfaces. Building it twice — once in a kiosk platform template, once in React for the partner app — means maintaining it in two places. Every time a resource category changes or a new UI pattern is needed, you update two systems instead of one.

🔒 Data Ownership & Privacy Pattern 1 Advantage
Pattern 1 — Custom Web App
All data flows from your PWA to Supabase — infrastructure you own and control. No vendor software layer sits between the user and your data. Session behavior, interaction patterns, and any analytics are entirely within CSAH's control.
Pattern 2 — Kiosk Content Platform
The platform's software layer sits between the kiosk and your data. Most kiosk content platforms collect session analytics on their own servers by default — that's how they demonstrate value to clients. Controlling what data leaves to vendor infrastructure requires active contractual negotiation, and in some cases isn't possible at all.
CSAH Impact The kiosk serves a vulnerable population. Per the data governance requirements established in the hardware comparison, behavioral data on unhoused users must not flow to vendor infrastructure. The LinkNYC case is the cautionary tale here — a public kiosk network whose advertising model meant user data became a product. Pattern 1 solves this by architecture. Pattern 2 requires negotiating against a vendor's business model.

⚙️ Long-term Flexibility Pattern 1 Advantage
Pattern 1 — Custom Web App
The kiosk surface can evolve as the project grows. Future integrations — a kiosk-to-app referral flow, a check-in system, a multilingual interface — are all buildable features in a custom codebase. You are not bounded by what a template platform supports.
Pattern 2 — Kiosk Content Platform
You are bounded by the platform's feature roadmap. If CSAH wants to add a kiosk feature the platform doesn't support — a custom interaction, an API integration, a non-standard UX flow — the answer is either "wait for the vendor to build it" or "switch platforms."
CSAH Impact The roadmap includes future kiosk → app integrations (e.g., a kiosk user requesting shelter generates a push notification to a partner team). That kind of feature requires a custom codebase. A template platform can't support it.

💰 Initial Build Complexity Tie (Pattern 2 easier up front)
Pattern 1 — Custom Web App
Requires a developer to build and maintain the kiosk app. More upfront work than template configuration. However: this is the same skillset already required for the partner app — no new tooling, no new team skills needed.
Pattern 2 — Kiosk Content Platform
Non-developers can configure and update content using the platform's visual tools. Lower initial build effort for a simple resource directory. The ceiling is low — the moment you need anything custom, you're back to developer time, except now it has to live outside the platform.
CSAH Impact ARC (Allyson + Alan) is doing all technical work. The team already has the skills for Pattern 1. The initial complexity advantage of Pattern 2 disappears the moment the kiosk needs anything the template platform doesn't support — which will happen.

Summary

Pattern 1 — Custom Web App  Leaning this way

  • Full UI control — designed specifically for the kiosk's audience and use case
  • Resource directory is built once, shared across kiosk and partner app
  • All session data stays in CSAH-controlled Supabase infrastructure
  • Same developer skillset as the partner app — no new tooling required
  • Extensible: future kiosk features are buildable, not blocked by platform limitations

Pattern 2 — Kiosk Content Platform

  • Lower initial build effort — non-developers can configure content
  • Requires maintaining resource directory in two separate systems
  • Session data collection is baked into most platform business models
  • Ceiling is the platform's feature set — custom interactions require switching tools
  • Future kiosk → app integrations are likely impossible within the platform

Our Lean — Part 1

Pattern 1. The kiosk content platform approach trades short-term convenience for long-term constraint — and creates a structural problem on data privacy that can't be fully resolved with a vendor whose revenue depends on session analytics. Pattern 1 is the right call for a project that needs a custom UX, shared code between two surfaces, and clean data ownership.

The kiosk software (Scalefusion, KioWare, or equivalent) is a container, not a content platform. It locks the browser to the kiosk URL and handles remote device management. It does not touch the data layer, does not define the UI, and does not replace what we're building.

Part 2 How to Structure the Two App Surfaces

Given Pattern 1, the question becomes: how do the kiosk app and the partner app relate to each other as codebases?

The reason this matters

The resource directory lives in both surfaces. Building it in two separate codebases means writing and maintaining it twice — every UI change, every data hook update, every accessibility improvement gets applied in two places. How tightly you couple the two apps determines how much of that duplication you avoid.

Option A

Two Separate Apps

Fully independent codebases, both calling Supabase

Pros
  • Simplest to set up
  • No coupling, no shared risk
  • Each app deployed independently
Cons
  • Resource directory written twice
  • Bug fixes applied in two places
  • Codebases drift over time
  • More repo management overhead
Option B  ·  Lean

Single App, Two Entry Points

One codebase, kiosk and partner routes as separate UI shells

Pros
  • Resource directory built and maintained once
  • Shared Supabase hooks, types, and logic
  • One repo, one deployment pipeline
  • Kiosk UI and partner UI share components where appropriate
  • Schema migrations apply to both surfaces at once — one migration run covers kiosk and partner app; no risk of surfaces running on different schema versions
Cons
  • Route guards required to keep kiosk users out of partner views
  • Slightly more complex initial routing setup
Option C

Monorepo + Shared Package

Shared component library; two separate app deployments

Pros
  • Cleanest separation of concerns
  • Shared code is versioned independently
  • Two deployment targets can diverge on different schedules
Cons
  • Monorepo tooling (Turborepo, Nx) adds setup overhead
  • Overkill for a two-surface app with one small team
  • Publish workflow for shared package adds friction

How Option B works in practice

One React app. Two route namespaces: /kiosk/* and /app/*. Each has its own layout shell — the kiosk shell is full-screen, large-type, touch-optimized, with no navigation to partner views. The partner shell has the full app chrome. Shared components — ResourceDirectory, Supabase data hooks, alert subscription logic, type definitions — live in a shared folder and are imported by both shells.

The kiosk lockdown software points to yourapp.com/kiosk. Route guards at the kiosk shell level ensure that even if a user somehow finds a link, they cannot navigate to /app. Authentication middleware on the /app routes provides a second layer of protection — the partner app requires login, which the kiosk never provides.

CSAH Impact The resource directory is maintained in one place. A change to how shelter information is displayed — format, fields, accessibility improvements — propagates to both the kiosk and the partner app automatically. This also means a single QA process, a single deployment pipeline, and no risk of the two surfaces drifting into inconsistency over time.

Our Lean — Part 2

Option B: single app, two entry points. The resource directory is the shared core of this project, and writing it once is clearly the right call. Option C (monorepo) is the more architecturally "correct" answer for a large team building long-term — it's the right answer for a different project. For a two-person team on a December deadline building two tightly related surfaces, the monorepo tooling adds friction without proportional benefit.

Option A is the only option we'd rule out now. Two codebases with a shared core is a maintenance debt that compounds. We'd spend more time keeping them in sync than building features.

No conflict with ADR-006 (Staging Strategy)

ADR-006 operates at the environment layer — which Supabase instance the build points at, controlled by environment variables set at deploy time. Option B operates at the routing layer — two URL namespaces within the same app. These are orthogonal. A single app with /kiosk/* and /app/* routes deploys to Netlify/Vercel as one unit, the same as any single-route app would. The environment variable swap is blind to how many routes exist.

One practical config check: Netlify/Vercel SPA redirect rules (/* → index.html) must be confirmed so that deep links to /kiosk and /app resolve correctly in both staging and production. On Netlify this is a one-line _redirects file — low risk, just needs to be in place before testing.

Open Questions

  1. Kiosk shell design: What does the kiosk landing screen look like — a directory immediately, or a simple "tap to start" attract screen that transitions to the directory? This affects the kiosk route structure and session reset behavior.
  2. Alert authoring interface: Who creates emergency/weather alerts, and what is the UI for it? This is a CSAH admin function (likely Kay or CSAH staff). A simple admin form in the partner app's admin panel is the likely answer — confirm the workflow before building the Supabase schema for alerts.
  3. Resource directory scope on kiosk vs. partner app: Is the kiosk directory a full match to what's in the partner app, or a curated subset? (e.g., should partner-specific internal resources appear on a public kiosk?) Needs a content decision before the shared component can be finalized.
  4. Option B validation: Confirm the single-app, two-entry-point routing structure works cleanly within the chosen deployment platform (Netlify or Vercel) and with Supabase Auth before the build phase begins.
